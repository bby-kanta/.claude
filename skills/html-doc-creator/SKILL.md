# HTML Doc Creator

固定デザインシステムで単一ファイルの HTML ドキュメントを作り、Artifact で公開するスキル。
CSS とスクロール連動 JS はテンプレートに完成品として全部入っているため、実作業は
「テンプレートをコピーして本文を組み立てる」ことに集中できる。

## 手順

### 1. テンプレートをコピーする

`assets/template.html` を Read し、スクラッチパッド（保存先の指定があればそちら）に
内容が分かる kebab-case のファイル名（例: `redis-latency-incident-report.html`）で Write する。

- CSS と scrollspy JS は検証済みの完成品。原則そのまま使う。
- 未使用コンポーネントの CSS が残っても害はない。削って回帰させるリスクの方が高いので削らない。

### 2. 本文を組み立てる

構成は自由。`references/components.md` のカタログを読み、内容に合うコンポーネントを選んで
`<main>` 内に配置する。**決まったセクション構成の縛りはない** — 内容が構成を決める。

- 結論が重要な文書（調査・障害報告）→ 冒頭に結論カード（verdict）
- 比較資料 → テーブル中心＋結論カード
- 手順書 → section＋番号付き見出しとテーブルだけでよい
- 指摘・課題が主役 → 深刻度ピル付きの指摘カード（finding）を並べる
- 処理や時系列の流れがある → フロー図（flow）

プレースホルダ（【…】）は必ず実コンテンツに置き換える。ダミーテキストを残さない。

### 3. 目次を同期する

- 各 `<section>` に `id="sec-1"` 形式の id、ジャンプさせたい小項目（指摘カード等）にも id を振る。
- `<nav class="toc">` 内のリンク href と id を一致させる。サブ項目はネストした `<ol>` で表す。
- セクションが 2 つ以下の短い文書では `<nav>` ごと削除し、`.layout` に `no-toc` クラスを付ける
  （`<div class="layout no-toc">`）。無意味な目次はノイズになる。

### 4. 検証する

公開前に次を確認する:

- 目次の全 href に対応する id が存在するか
- タグの閉じ忘れ・属性クォート漏れがないか
- 横幅が出る要素（テーブル・長いコード・図）が overflow コンテナ
  （`.table-wrap` / `.flow-wrap`）に入っているか — 本文が横スクロールしたら失敗

### 5. Artifact で公開する

Artifact ツールで公開し、URL をユーザーに返す。

- `favicon`: 文書の主題に合う絵文字 1 つ。再公開時も変えない（タブの識別子になるため）。
- `description`: 文書の内容を一文で。
- 同じファイルパスへの再公開は同じ URL を保つ。修正依頼が来たらファイルを編集して再公開する。
- ローカル保存だけを求められた場合は公開をスキップしてファイルパスを返す。
- 公開前に artifact-design スキルのロードが求められる環境ではロードしてよいが、
  本スキルのテンプレートを「既存デザインシステム」として優先適用する
  （artifact-design 自体が既存システムの尊重を最優先と定めている）。

### 6. ローカルブラウザで開く

生成した HTML ファイルをローカルブラウザでも開いてユーザーがすぐ確認できるようにする
（macOS なら `open <ファイルパス>`）。

- サンドボックス内の `open` は LaunchServices に接続できず
  `procNotFound: no eligible process with specified descriptor` で失敗することがある。
  このエラーが出たら sandbox を外して（dangerouslyDisableSandbox）再実行する。
- ヘッドレス環境・リモート環境などブラウザを開けない場合はスキップし、
  ファイルパスと Artifact URL を返すだけでよい。

## デザイン不変条件

テンプレートに手を入れる必要が生じたときも、以下は壊さないこと。

- **色は必ず CSS 変数経由で参照する。** ハードコードするとダークテーマで破綻する。
  テーマは「`:root`（ライト既定）→ `@media (prefers-color-scheme: dark)` →
  `:root[data-theme=...]` 上書き」の 3 段構成で、閲覧者のテーマトグルが最優先になる設計。
- **目次は grid ＋ `position: sticky`。`position: fixed` にしない。**
  fixed は文書フローから外れ、本文との横位置を手計算する必要が生じ、フッター到達時に破綻する。
  sticky ならグリッドが幅と位置を管理する。
- アンカージャンプの着地位置は `[id] { scroll-margin-top }` が制御している。見出しが
  画面上端に張り付くようなら、この値を調整する（個別 margin で対処しない）。
- **深刻度・状態の色（ピル 5 種）とアクセント色（インディゴ）は役割が別。**
  強調したいだけの箇所にセマンティックカラーを流用しない。
- 数値が縦に並ぶテーブル列は `td.num`（tabular-nums で桁が揃う）。
- スクロール連動ハイライトは「scrollY を超えた最後のターゲットを現在地とする」走査方式。
  IntersectionObserver に置き換えない — セクション高がバラバラな文書では
  「画面に少し見えただけで反応する」IO 方式より現在地が安定する。

## ライティング

- リード文・結論カードは結論から書く。読者が最初の 3 行で「何が起きたか / 何をすべきか」を
  掴めるようにする。
- ファイルパス・コマンド・識別子・設定値は `<code>` で囲む。
- セクション番号やマーカー（① ② …）は、順序・優先度に実際の意味があるときだけ使う。
  装飾のために番号を振らない。
- テーブルのセルは短く保ち、説明・補足は前後の本文か `.note` に書く。
- 参照元（PR 番号・ファイルパス・URL・日付）を残す。ドキュメントは書いた瞬間から古びるので、
  読者が一次情報に戻れるようにしておく。
