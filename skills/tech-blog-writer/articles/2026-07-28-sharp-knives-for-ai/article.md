# Rails Doctrineを、大AIエージェント時代に読み直し、思想を体現できているかを調査した

こんにちは、エスカレーターの右側（関西では左側）で最初に止まる人は英雄です。たろう眼鏡です。
たろう眼鏡も隙あらば止まって英雄活動をしています。

ところで先日、[Rails Doctrine](https://rubyonrails.org/doctrine/ja)を読み直す機会がありました。2016年にDHHが書いた、Railsの設計思想をまとめた文書です。
読み直したついでに、普段開発しているレシチャレのRailsリポジトリが、Rails Doctrineの教えにどこまで沿えているのか調査してみました。

そうしたら、「鋭いナイフを提供する（Provide Sharp Knives）」の章が、AIエージェント時代の今読むほうがずっと刺さる内容になっていました。今回はその話を書きます。

## DHHは止める仕組みを作らなかった

「鋭いナイフを提供する」は、Rubyのモンキーパッチ（既存クラスの再オープンや上書き）などを擁護する章です。簡単にいうと「危険な機能を言語仕様で禁止するのではなく、プログラマーを信頼して渡す」という宣言です。

> There's nothing programmatically in Ruby to stop you using its sharp knives to cut ties with reason. We enforce such good senses by convention, by nudges, and through education.
>
> — [The Rails Doctrine "Provide sharp knives"](https://rubyonrails.org/doctrine#provide-sharp-knives)

ナイフの乱用を止めるシステム的な仕組みは、Rubyには何もない。歯止めは慣習と、注意の呼びかけと、教育。仕組みではなく文化で止める、と言い切っています。

面白いのは、ナイフ批判の構造を見抜いているところです。DHH曰く、"I can't trust myself with this power, please take it away from me!"（この力を使いこなせる自信がないから、取り上げてくれ）と手を挙げるプログラマーは見たことがない。批判は決まって"I think **other programmers** would abuse this"（他のプログラマーはこれを乱用すると思う）の形をとる、と。

2016年の文章ですが、"other programmers"を「AI」に置き換えると、そのまま2026年の議論になると考えました。Claude Codeにコードベースを触らせるとき、私たちが心配しているのはまさに「AIはこのような鋭いナイフを乱用するだろう」ということです。

次からの章では、弊リポジトリがナイフとどう付き合ってきたのかを調査した結果を紹介します。

## 調査したら、ナイフはほぼ鞘の中だった

弊リポジトリを対象に、Rubyの「鋭いナイフ」の使用箇所を調査した結果がこちらです👇️

| 機能 | 使用箇所 |
|---|---|
| `default_scope` | 0件 |
| STI（単一テーブル継承） | 0件 |
| `method_missing` | 0件 |
| `Module#prepend` / refinement | 0件 |
| `class_eval` / `alias_method` | 0件 |
| コアクラスのモンキーパッチ | 1ファイル |
| `update_column` | 3件 |
| `find_by_sql` | 1件 |

モデルのコールバックも338モデル中33件（約10%）に収まっていました。

Railsで一番事故りやすいと言われるdefault_scopeが0件。モンキーパッチも実質1ファイル。gem選定も同じ傾向でした。paranoiaやdeviseのような、挙動を大きく書き換える系は入っていません。入っているのはstrong_migrations、bullet、brakeman、committee-railsといったガードレール側ばかりです。

正直、調査するまでここまで禁欲的だとは思っていませんでした。Rubyは何でもできる言語なのに、「抜かない」選択が続いていた。誰かが明文化したわけでもなく、既存コードに合わせるといういい意味の同調圧力が働き続けた結果だと思います。

Doctrineの言う「慣習による自制」が、リポジトリの寿命スケールでちゃんと機能した例です。

## 抜くときは、理由を横に書く

全部封印しているわけではなくて、抜くときは抜きます。抜いた場所には、「なぜ安全か」のコメントが必ずセットで付いています。

たとえばガラポンの在庫デクリメント。バリデーションをスキップするupdate_allを使っています。

```ruby
# app/models/garapon_prize.rb
where("remaining_stock > 0").update_all("remaining_stock = remaining_stock - 1")
```

これだけ見ると「バリデーション飛ばしてるじゃん」ですが、同じファイルに設計判断が書いてあります。「当選レコード存在時の在庫変更はupdate_all経由（delta加算）でのみ許可する。ActiveRecord validationはupdate_allをスキップするため、両経路と整合する」。競合を避けるためのアトミックな更新で、バリデーションを飛ばすこと自体が設計だと分かります。

update_columnの3件のうち2件にも「updated_atを更新しないためにupdate_columnを使う」という理由コメントが付いていました。DynamoDBを絡めたコイン付与処理には、こんなコメントもあります。

```ruby
# DynamoDB GSI経由の読み取りは結果整合のため、同時リクエストはすり抜け得る。
# ここは一次防壁で、最終防壁はコイン基盤のUNIQUE制約
```

ナイフを抜くこと自体は禁止しない。ただし抜いた理由をその場に書く。レビューで「なんでここupdate_allなんですか」と聞かれる前に答えが書いてある状態です。

## それでも指は切れる

ここまでだと自画自賛ブログなんですが、調査では血の跡も見つかりました。3つ紹介します。

### 唯一のモンキーパッチに、罠が3つ全部乗っていた

弊リポジトリで唯一のコアクラス拡張が`lib/string.rb`です。全24行。

```ruby
class String
  class TypeError < StandardError; end

  # 中略

  # input: "78decb5b644241a0be773d17dd146c49"
  def to_uuid
    raise TypeError.new("invalid uuid format") if self.length != 32 || !self.match(/[0-9a-z]/)[0] == self

    self.insert(8, "-").insert(13, "-").insert(18, "-").insert(23, "-")
  end
end
```

この24行に、独立した問題が3つあります。

1. **`String::TypeError`が組み込みの`::TypeError`を隠している。** Stringクラスの内側で定義しているので、このTypeErrorはStandardErrorの子であって、組み込みの::TypeErrorの子孫ではありません。呼び出し側が`rescue TypeError`と書いてもすり抜けます
2. **`to_uuid`が破壊的。** `String#insert`はレシーバ自身を書き換えるので、`params[:user_id].to_uuid`のような呼び出しはパラメータを直接汚染します
3. **バリデーションが死んでいる。** `!self.match(/[0-9a-z]/)[0] == self`は演算子の優先順位で`(!match[0]) == self`と解釈されて常にfalse。実質、長さ32のチェックしか効いていません

3番はLint系のcopが有効なら機械的に見つかるレベルです。でも見つからなかった。モンキーパッチが置いてあったのはlib/の下、つまり「レビューの目が届きにくい場所」です。9箇所から呼ばれていたのに、誰も気づきませんでした。

「慣習と相互の注意と教育」は、目が届く場所でしか機能しない。当たり前ですが、それが実バグ3つで確認できてしまいました。

### 自分で成文化したルールに、コードが違反したまま残っている

弊リポジトリには`.claude/rules/`というディレクトリがあって、AIエージェント向けのコーディング規約が19ファイル分書かれています。「エラーは握り潰さず必ず処理すること」「トランザクションは必ずApplicationRecord.transactionを使う（マルチDB構成のため）」といった内容です。

で、コードを見ると。

```ruby
# app/models/special_offer.rb
after_create do
  # 中略
rescue => _
  # エラーが発生したらスキップする
end
```

全例外を握り潰すafter_createが、ルールと同じリポジトリに同居しています。ActiveRecord::Base.transactionも2件残っていました。

ルールが間違っているわけでも、書いた人が悪いわけでもありません。問題は、ルールがAI向けドキュメントにしか存在せず、**CIがルールを知らない**ことです。人間もAIも、ドキュメントを読んだときだけルールに従える。読まなかったときに止める仕組みがない。

### Service層は「入口」だけ規約があり「出口」が無法地帯

弊リポジトリのService層は354ファイルあって、命名は驚くほど統一されています。ファイル名の95.5%が`*_service.rb`、公開メソッドは`run`が295件、コミュニティ標準の`call`は0件。ここまで揃っていると正直気持ちいいです。

ただ、戻り値を数えたら急に無法地帯でした。

- ActiveRecordモデルを返す
- Hashを返す
- Booleanを返す
- nil / String / Symbolを状況によって返し分ける
- クラス内にローカル定義した使い捨てのResult Structを返す（3ファイルがそれぞれ独自定義）

例外方針も「積極的にraiseする派」と「StandardErrorまでrescueしてSlack通知して握り潰す派」が併存していて、呼び出し側は結局、個々のServiceの実装を読まないと安全に使えません。

入口の規約は「隣のファイルを見ればわかる」ので同調圧力が働く。出口の規約は「呼び出し側まで読まないとわからない」ので働かない。慣習ベースの統制が何に強くて何に弱いか、綺麗に出た例だと思います。

## で、AIが来た

指を切った3つの例に共通するのは、「慣習・相互の注意・教育」という人間向けの自制メカニズムには射程距離がある、ということでした。目が届く場所（入口の命名）では完璧に機能して、届かない場所（lib/の下、戻り値、CIが知らないルール）では機能しない。

そこにAIエージェントが来ました。AIは人間の何倍もの速度でコードを書きます。「相互の注意」の目が追いつく前に、次のコードが積まれていく。DHHが人間相手に答えた「ナイフを渡すか」という問いに、今度はAI相手に答える必要が出てきたわけです。

弊リポジトリでは、この問いへの答えが`.claude/`配下に実装されています。調査していて面白かったのは、「渡す・渡さない」の二択ではなく、**ナイフの渡し方が3段階のグラデーション**になっていたことです。

### レベル1: そもそも渡さないナイフ

PreToolUseフック（safety_guard.sh）が、`gh pr merge`、`git push --force`、`DROP TABLE`などをAIの判断を介さずに遮断します。AIが「マージしていいですか」と聞く余地すらありません。シェルスクリプトなので、AIの気分にも左右されません。

金額計算も同じ扱いです。always-human-review.txtという、たった4行のテキストファイルがあります。ここに載っているインセンティブ計算などのファイルは、AIレビューで完結させず必ず人間レビューに回す。判定するのはシェルスクリプトなので、こちらも決定論的です。

### レベル2: 人間にエスカレーションするナイフ

terraformやECSタスク定義など、リポジトリの外に影響するものはhuman_interventionという分類で、AIの自律ループから人間に差し戻されます。理由も明文化されていて「実装エージェントはこのリポジトリ内しか触れないので、リトライさせても直らない」から。AIに再試行させても無駄な領域を、構造的に見分けています。

### レベル3: 手順書つきで渡すナイフ

他リポジトリへの書き込みのような危険な操作も、禁止はせず手順書つきで渡します。原則はこうです。「対象リポジトリにCLAUDE.mdがある場合、矛盾したら相手のルールを優先する」。相手の家では相手のルールに従う、です。

あと個人的に一番好きなのが、自律実装フローのルールにあるこの一文です。

> 全chunk完了後はユーザーに確認を求めずPR作成まで自動実行する。PR作成可否をユーザーに尋ねることは禁止

**確認しすぎることの方を禁止している。** DHHはDoctrineの中で"That line of paternalism has never appealed to me."（そういう父権主義に魅力を感じたことはない）と書いていますが、その裏返しがここにあります。信頼して渡すと決めた範囲では、お伺いを立てさせない。

## 規約を増やす規約

もうひとつ、Doctrineと綺麗に対応していたのが「ルール自体の増やし方」です。

Convention over Configurationの強さは、規約を増やしすぎない自制とセットで成立しています。何でもかんでも規約にしたら、それはただの分厚い社内ルールブックです。

`.claude/rules/`にルールを追加するには、専用のフローを通ります。

1. 実装ミスやレビュー指摘が発生する
2. 振り返りで分類する。**1回だけなら個人のTILで終わり。2回以上繰り返されたらルール化候補**
3. ルール追加の審査。基準は「**この行を削除したらAIが間違えるか？ Noなら追加しない**」

「Rubyの標準的なベストプラクティス」や「コードを2〜3ファイル読めば分かるパターン」は明示的に却下されます。AIが既存コードから読み取れることをルールに書くのは、コンテキストの無駄遣いだからです。

ルールを書くコストは、書いた瞬間には終わりません。そのルールは全セッションで読み込まれ続けますし、いつか陳腐化して嘘になるリスクも抱えます。「規約は増やさないほど強い」というCoCの原理が、AI向けルールでも同じ形で再発明されていました。

## 分割の基準も、渡さない基準も「お金」だった

最後に、調査で一番「設計思想が言語化されてるな」と感じた話を。

弊リポジトリはかなり過激なモノリスです。1つのコードベースをENVフラグで15のECSサービスとして起動し分けていて、管理画面もAPIもバッチも全部同居しています。DHHの言うマジェスティックモノリスを、ある意味で超えている。

そのモノリスに、例外が1つだけあります。コインの残高管理だけが、別リポジトリのマイクロサービスに分離されています。

ここで、さっきのAIレビュー禁止リスト（always-human-review.txt）を思い出してください。あそこに載っているのも金額計算のファイルでした。

- モノリスから分割する基準 → お金
- AIに渡さない基準 → お金

アーキテクチャの境界とAIへの委任境界が、同じ判断基準で引かれています。「本当に必要になるまで分散を避けよ」というDoctrineの教えの裏返しで、このチームにとっての「本当に必要」は金銭ドメインでした。誤動作したときに取り返しがつかない領域だけが、モノリスからも信頼からも切り出されている。

境界の判断基準が言語化されているモノリスは強いです。次に何かを分割するか迷ったとき、「それはお金か？」という問いから始められるので。

## まとめ

Rails Doctrineの健康診断から始まって、AIへのナイフの渡し方の話になりました。

- ナイフを抜かない慣習は、リポジトリの寿命スケールで機能していた（default_scope 0件）
- ただし慣習には射程距離があって、目の届かない場所では指を切っていた（モンキーパッチの罠3つ、CIが知らないルール、Serviceの出口）
- AI時代の答えは「信頼するか否か」の二択ではなく、決定論的ブロック・人間へのエスカレーション・手順書つきで渡す、のグラデーション
- ルールを増やすことにもルールがある（「この行を削除したらAIが間違えるか？」）
- モノリスの分割基準もAIに渡さない基準も「お金」で一貫していた

DHHは「プログラマーを信頼して鋭いナイフを渡す」と書きました。10年経って、渡す相手にAIが加わりました。やることは変わらなくて、信頼を雰囲気ではなく構造にすることなんだと思います。シェルスクリプト4行の禁止リストも慣習も、どちらも信頼の構造です。違いは、書く速度に耐えられるかどうかだけ。

みなさんのリポジトリのナイフ事情も、ぜひ数えてみてください。default_scopeが0件だったら、それは誰かが守り続けた慣習です💚

Keep your knives sharp! 🔪
