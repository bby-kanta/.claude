# Rails Doctrineを、大AIエージェント時代に読み直し、思想を体現できているかを調査したぞ

こんにちは、エスカレーターの右側（関西では左側）で最初に止まる人は英雄です。たろう眼鏡です。
たろう眼鏡も隙あらば止まって英雄活動をしています。

ところで先日、[Rails Doctrine](https://rubyonrails.org/doctrine/ja)を読み直す機会がありました。2016年にDHHが書いた、Railsの設計思想をまとめた文書です。
読み直したついでに、普段開発しているレシチャレのRailsリポジトリが、Rails Doctrineの教えにどこまで沿えているのか調査してみました。

そうしたら、「鋭いナイフを提供する（Provide Sharp Knives）」の章が、AIエージェント時代の今読むほうがずっと刺さる内容になっていました。今回はその話を書きます。

## DHHは止める仕組みを作らなかった

「鋭いナイフを提供する」は、例えばRubyのモンキーパッチ（既存クラスの上書き）などを擁護する章です。簡単にいうと「危険な機能を言語仕様で禁止するのではなく、プログラマーを信頼して渡す」という宣言です。

> There's nothing programmatically in Ruby to stop you using its sharp knives to cut ties with reason. We enforce such good senses by convention, by nudges, and through education.
>
> — [The Rails Doctrine "Provide sharp knives"](https://rubyonrails.org/doctrine#provide-sharp-knives)

ナイフの乱用を止めるシステム的な仕組みは、Rubyには何もない。歯止めは慣習と、注意の呼びかけと、教育。仕組みではなく文化で止める、と言い切っています。

なぜ仕組みで縛らないのか。禁止すると、良い使い方まで一緒に死ぬからです。危険かどうかは文脈でしか決まらず、文脈を判断できるのは人間だけ。だから判断する主体を、仕組みではなく人間に置いたわけです。

でも、これは難しい問題です。悪い使い方が暴走するリスクが怖くて、結局仕組みで縛ったり、使わないという選択を深く検討もしないまましてしまいます。

DHH曰く、「自分にはこの力を使いこなせる自信がないので、取り上げてください！」（"I can't trust myself with this power, please take it away from me!"）と手を挙げるプログラマーは見たことがない。聞こえてくるのは決まって「どうせ**他のプログラマー**が乱用する」（"I think **other programmers** would abuse this"）という声だ、と。

要するに、ナイフを危ないと言う人も、自分の腕は疑っていないんです。取り上げたい理由は、いつも自分ではなく他人を疑っていると。

2016年の文章ですが、"other programmers"を「AI」に置き換えると、そのまま2026年の議論になると考えました。Claude Codeにコードベースを触らせるとき、我々が心配しているのはまさに「AIはこのような鋭いナイフを乱用するのでは」ということです。

次からの章では、弊リポジトリが鋭いナイフとどう付き合っているのかを調査した結果を紹介します。

## 調査したら、ナイフはほぼ鞘の中だった

弊リポジトリを対象に、Rubyの「鋭いナイフ」の使用箇所を調査した結果がこちらです👇️

| 機能 | 使用箇所 | 何が鋭いか |
|---|---|---|
| `default_scope` | 0件 | 全クエリに暗黙の条件が混入し、外し忘れに気づけない |
| STI（単一テーブル継承） | 0件 | 1テーブルを複数クラスで共有し、型が増えるほどスキーマが歪む |
| `method_missing` | 0件 | 呼び出し先のメソッドが実在せず、定義ジャンプもgrepも効かない |
| `Module#prepend` / refinement | 0件 | メソッド探索順を書き換え、挙動の出どころが追えなくなる |
| `class_eval` / `alias_method` | 0件 | 既存メソッドを実行時に書き換え、影響範囲が静的に読めない |
| コアクラスのモンキーパッチ | 1ファイル | Stringなどの挙動変更が、全コード・全gemに波及する |
| `update_column` | 3件 | バリデーションもコールバックも黙ってスキップする |
| `find_by_sql` | 1件 | 生SQLがARの抽象を素通りし、スキーマ変更に取り残される |
| モデルのコールバック | 33件（338モデル中） | 保存や削除に処理が暗黙に連鎖し、1回のsaveで何が起きるか読めなくなる |

Railsで一番事故りやすいと言われるdefault_scopeが0件。モンキーパッチも実質1ファイル。

思ったより禁欲的でした（笑）Rubyは何でもできる言語なのに、「抜かない」選択が続いていたように見えます。
とはいえ全く抜かないわけではないので、鋭いナイフがジョーカーとして機能しているようです。

鋭いナイフの禁止を特段誰も明文化しているわけではないので、既存コードに合わせる・鋭いナイフは極力使わないという良い意味の同調圧力が働き続けた結果だと推測します。

Doctrineの言う「慣習による自制」が、リポジトリの寿命スケールでちゃんと機能した例です。

## 抜くときは、Whyをコメントに書く

全部封印しているわけではなくて、抜くときは抜いています。抜いた場所には、「なぜ安全か」のコメントが必ずセットで付いていました。

たとえば景品在庫の払い出し。バリデーションをスキップするupdate_allを使っている箇所は、こんな形になっています（実コードを単純化しています）。

```ruby
# 在庫の更新はこの update_all（相対加算）経由のみ許可する。
# 読み取ってから保存する方式だと、同時リクエストで在庫がマイナスになり得るため、
# 条件付きのアトミックな UPDATE にしている。
# validation はスキップされるが、この経路に限ってはそれが意図した挙動。
Prize.where("remaining_stock > 0")
     .update_all("remaining_stock = remaining_stock - 1")
```

これだけ見ると「バリデーションを飛ばしちゃってるじゃん」となるところに、なぜ飛ばすのが正しいかが横に書いてある。
ナイフを抜くこと自体は禁止しない。ただし抜いた理由をその場に書く。レビューで「なんでここupdate_allなんですか」と聞かれる前に答えが書いてある状態です。

弊リポジトリのCLAUDE.mdには「コードコメントには、What・Howを羅列するのではなく、Why・Why notを記載する」という記述があります。
鋭いナイフ活用時には特にこのルールが重要です。

## それでも指が切れるときは切れる

ここまでだと自画自賛ブログなんですが、調査では血痕も見つかりました。3つ紹介します。

### 唯一のモンキーパッチに罠が仕掛けられていた

弊リポジトリで唯一のコアクラス拡張がありました。

```ruby
class String
  class TypeError < StandardError; end

  # 中略

  def to_uuid
    raise TypeError.new("invalid uuid format") if self.length != 32 || !self.match(/[0-9a-z]/)[0] == self

    self.insert(8, "-").insert(13, "-").insert(18, "-").insert(23, "-")
  end
end
```

このコードに、独立した問題が3つあります。

1. **`String::TypeError`が組み込みの`::TypeError`を隠している。** Stringクラスの内側で定義しているので、このTypeErrorはStandardErrorの子であって、組み込みの::TypeErrorの子孫ではありません。呼び出し側が`rescue TypeError`と書いてもすり抜けます
2. **`to_uuid`が破壊的。** `String#insert`はレシーバ自身を書き換えるので、`params[:user_id].to_uuid`のような呼び出しはパラメータを直接汚染します
3. **バリデーションが死んでいる。** `!self.match(/[0-9a-z]/)[0] == self`は演算子の優先順位で`(!match[0]) == self`と解釈されて常にfalse。実質、長さ32のチェックしか効いていなかった

モンキーパッチは便利な反面、思わぬバグを混入させる危険性を孕んでいます。
組み込み関数は基本的には全幅の信頼を置けるクラスですが、実はモンキーパッチで意図せず前提や振る舞いを変えている可能性があります。
ナイフの鋭さを知るには、自分の指を切るのが一番です。

## で、AIが来た

指を切った3つの例に共通するのは、「慣習・相互の注意・教育」という人間向けの自制メカニズムには射程距離がある、ということでした。目が届く場所（入口の命名）では完璧に機能して、届かない場所（lib/の下、戻り値、CIが知らないルール）では機能しない。

そこにAIエージェントが来ました。AIは人間の何倍もの速度でコードを書きます。「相互の注意」の目が追いつく前に、次のコードが積まれていく。

もうひとつ、速度より根深い問題があります。文化による歯止めは、相手が教育を蓄積することが前提です。人間の同僚は、レビューで指摘されたことを覚えていて次からは直る。でもAIエージェントはセッションごとに記憶がリセットされます。教育が積み上がらない相手に、慣習・注意・教育は効かない。

DHHが人間相手に答えた「ナイフを渡すか」という問いに、今度はAI相手に答え直す必要が出てきたわけです。

弊リポジトリでは、この問いへの答えが`.claude/`配下に実装されています。調査していて面白かったのは、「渡す・渡さない」の二択ではなく、**ナイフの渡し方が3段階のグラデーション**になっていたことです。

### レベル1: そもそも渡さないナイフ

PreToolUseフック（safety_guard.sh）が、`gh pr merge`、`git push --force`、`DROP TABLE`などをAIの判断を介さずに遮断します。AIが「マージしていいですか」と聞く余地すらありません。シェルスクリプトなので、AIの気分にも左右されません。

### レベル2: 人間にエスカレーションするナイフ

terraformやECSタスク定義など、リポジトリの外に影響するものはhuman_interventionという分類で、AIの自律ループから人間に差し戻されます。理由も明文化されていて「実装エージェントはこのリポジトリ内しか触れないので、リトライさせても直らない」から。AIに再試行させても無駄な領域を、構造的に見分けています。

### レベル3: 手順書つきで渡すナイフ

他リポジトリへの書き込みのような危険な操作も、禁止はせず手順書つきで渡します。原則はこうです。「対象リポジトリにCLAUDE.mdがある場合、矛盾したら相手のルールを優先する」。相手の家では相手のルールに従う、です。

あと個人的に一番好きなのが、自律実装フローのルールにあるこの一文です。

> 全chunk完了後はユーザーに確認を求めずPR作成まで自動実行する。PR作成可否をユーザーに尋ねることは禁止

**確認しすぎることの方を禁止している。** DHHはDoctrineの中で"That line of paternalism has never appealed to me."（そういう父権主義に魅力を感じたことはない）と書いていますが、その裏返しがここにあります。信頼して渡すと決めた範囲では、お伺いを立てさせない。

こうして見ると、これは文化を捨てて仕組みに乗り換えた話ではないんですよね。`.claude/rules/`は文化の外部記憶で、hooksは「相互の注意」の自動化。記憶を持たない同僚のために、文化を実行可能な形に翻訳したものです。

## 一番効いているルールは「既存に従え」

`.claude/rules/`の先頭には、派手さのかけらもない原則が置いてあります。

> - 新しいパターンを発明しない。既存の実装パターンに合わせる
> - 類似機能の既存実装を先に調査し、そのパターンに従う

一見どこのリポジトリにもありそうな一文ですが、調査を終えたあとだと、これが一番効いているルールに見えてきます。

思い出してほしいのは、ナイフが鞘に収まっていた経緯です。誰かが禁止したわけではありませんでした。
有識者が「コールバックやdefault_scopeは危ないから使いたくない」と言い、聞いていたメンバーが「確かに」と空気を読み、使わないコードが積み上がっていった。判断の経緯は特に文書化されているわけではありません。残ったのは、ナイフを使わなかったコードベースそのものです。

そこに「既存の実装パターンに合わせる」というルールを置くとどうなるか。default_scopeが0件のコードベースを調査したAIは、default_scopeを書きません。かつての有識者の判断が、コードを経由して今日のAIに伝播する。文化の記録媒体はコードベースで、「既存に従え」はその再生装置です。

空気を読んでいたのは、人間だけじゃなかったわけです。

## 規約を増やす規約

もうひとつ、Doctrineと綺麗に対応していたのが「ルール自体の増やし方」です。

Convention over Configurationの強さは、規約を増やしすぎない自制とセットで成立しています。何でもかんでも規約にしたら、それはただの分厚い社内ルールブックです。

`.claude/rules/`にルールを追加するには、専用のフローを通ります。

1. 実装ミスやレビュー指摘が発生する
2. 振り返りで分類する。**1回だけなら個人のTILで終わり。2回以上繰り返されたらルール化候補**
3. ルール追加の審査。基準は「**この行を削除したらAIが間違えるか？ Noなら追加しない**」

「Rubyの標準的なベストプラクティス」や「コードを2〜3ファイル読めば分かるパターン」は明示的に却下されます。AIが既存コードから読み取れることをルールに書くのは、コンテキストの無駄遣いだからです。

ルールを書くコストは、書いた瞬間には終わりません。そのルールは全セッションで読み込まれ続けますし、いつか陳腐化して嘘になるリスクも抱えます。「規約は増やさないほど強い」というCoCの原理が、AI向けルールでも同じ形で再発明されていました。

## まとめ

Rails Doctrineの健康診断から始まって、AIへのナイフの渡し方の話になりました。

- ナイフを抜かない慣習は、リポジトリの寿命スケールで機能していた（default_scope 0件）
- ただし慣習には射程距離があって、目の届かない場所では指を切っていた（モンキーパッチの罠3つ、CIが知らないルール、Serviceの出口）
- AI時代の答えは「信頼するか否か」の二択ではなく、決定論的ブロック・人間へのエスカレーション・手順書つきで渡す、のグラデーション
- 文化はコードベースに保存されている。「既存に従え」ルールが、それをAIに再生させる
- ルールを増やすことにもルールがある（「この行を削除したらAIが間違えるか？」）

DHHは「プログラマーを信頼して鋭いナイフを渡す」と書きました。10年経って、渡す相手にAIが加わりました。やることは変わらなくて、信頼を雰囲気ではなく構造にすることなんだと思います。PreToolUseフックも慣習も、どちらも信頼の構造です。違いは、AIの速度と物忘れに耐えられるかどうかだけ。

最後に、逆向きの話も。ここまで「AIにどうナイフを渡すか」という守りの話をしてきましたが、ハーネスが揃った今なら、逆のことも言えるはずです。人間が空気を読んで封印してきたナイフを、AIに使わせてみる。AIはRubyのセマンティクスを人間より正確に知っていて、疲れないし、hooksとCIとレビューが常に見張っています。慣習と教育しか歯止めがなかった時代の封印を、ガードレールが揃った時代まで引きずる必要はないのかもしれません。DHHが人間に渡したナイフを、AIにだけ渡さない理由は、もうない気がしています。
適切な文化を形成したうえで、AIに鋭いナイフを解禁していくことを検討してみるのも、面白い選択肢かもしれません。

みなさんのリポジトリのナイフ事情も、ぜひ数えてみてください。default_scopeが0件だったら、それは誰かが守り続けた文化です💚

Keep your knives sharp! 🔪
